# RAG 知识库问答：检索链路与工程设计

## 0. 技术栈
Python、LangChain、DashScope embedding（文本向量化，约 512 维，以代码为准）、Milvus（向量数据库）、DeepSeek（生成）、loguru。

## 1. 三档项目介绍
### 一句话
一个基于 Milvus 的私有知识库 RAG 问答系统，离线把文档切块向量化入库，在线做查询改写、向量检索、Rerank 精排和带来源的生成，并带重检索闭环和未提及兜底。

### 30 秒
分离线和在线两条链路：离线把文档清洗后用递归字符分块、块间留重叠，调 embedding 向量化连同来源元数据存进 Milvus；在线先把用户问题做查询改写，再向量检索 top-k、按文本去重、Rerank 精排，最后把片段拼成 context 交给大模型生成并标注来源。还加了评审节点，检索内容答不了就带反馈重检索最多两次，检索不到就明确说"资料未提及"，防止模型脱离知识库瞎编。

### 详细说明
> 这是一个基于 Milvus 的私有知识库问答系统，走标准 RAG，分离线入库和在线问答。离线侧先清洗文档，去控制字符、统一换行和空格；再用递归字符分块，按段落、换行、句号逐级切，优先在自然语义边界断开，块间留 50 的重叠防止信息在接缝处丢失；然后调 DashScope 的 embedding 把每个 chunk 向量化，连同"来自哪个文档第几页"的元数据一起存进 Milvus。
>
> 在线侧，用户提问后先做查询改写，把口语化问题转成规范检索词；只把问题向量化，去库里和预存 chunk 向量算余弦相似度取 top-k、按文本去重，再用 Rerank 精排把最相关的顶上来；最后把片段拼成 context 连同问题交给大模型生成并标注来源。我加了评审闭环，判断资料能不能回答问题、不行带反馈重检索最多两次；检索为空就明确回复"知识库未提及"，不让模型裸编。它解决大模型不懂私有知识、知识截止和幻觉问题，相比微调成本低、知识可随时更新、可溯源。

## 2. 两条链路主线
```
【离线入库】文档 → 清洗 → 递归分块(overlap=50) → 每块 embedding 成一个向量 → 连来源元数据存 Milvus
【在线问答】问题 → 查询改写 → 问题向量化 → 余弦相似度 top-k 检索 → 按文本去重
          → Rerank 精排 → 拼 context → LLM 生成(带引用) → 评审(不行重检索≤2) → 答案+溯源
```
关键：**一个 chunk = 一条记录 = 一个向量（不是每个 token 一个向量）**；在线只给问题算向量，chunk 向量离线已算好。

## 3. 每一步为什么这么设计
- **清洗**：控制字符/乱码、统一换行、去行尾空格、压缩连续空行，否则向量化不准。
- **递归分块**：按 段落→换行→句号 优先级逐级切，优先在自然边界断，避免固定字数把句子/语义切断。
- **overlap=50**：相邻块留重叠，防止关键信息正好落在切分边界被劈成两半。
- **chunk 大小权衡**：太小语义残缺、块多噪声大；太大一个块多主题、向量被稀释变"糊"、费 token、溯源不精。原则是一块承载一个完整且单一的语义单元。
- **embedding**：把整段映射成固定维向量（语义空间坐标），模型训练保证语义近向量近；支持语义匹配（"咋用"能匹配"使用方法"），优于关键词字面匹配。
- **Milvus**：用 ANN 索引(HNSW/IVF)做大规模快速最近邻检索，避免全量暴力计算；一条记录=向量+原文+来源元数据，支持持久化和元数据过滤。
- **查询改写**：口语/模糊/多意图问题直接检索召回差，改写成规范检索词（可扩多个）提升召回。
- **Rerank**：向量检索是粗排（快但整体语义相似），交叉编码器把"问题+每个候选块"一起精算是精排；粗排保召回、精排保精度。
- **溯源**：入库时存 source/page，检索连带返回，生成要求标引用，可回原文核查、降幻觉。**溯源是自己设计的元数据，不是 Milvus 自带。**

## 4. 高频追问 · 标准答案
**Q1 完整流程？** 见第 1、2 节，强调离线/在线分开。
**Q2 为什么递归分块、overlap 作用、块太大太小？** 见第 3 节。
**Q3 是每个 token 一个向量吗？** 不是，模型内部逐 token 有 hidden，但经池化(pooling)后整段 chunk 输出一个向量；类比 DNABERT 整条序列池化成序列表示。
**Q4 凭什么语义近向量就近？** embedding 在海量文本上训练，目标就是让语义/上下文相似文本向量距离近；用余弦相似度（方向越一致越接近 1）。
**Q5 为什么用向量库、Python 算不行吗？** 小数据 numpy 全量算可以；上量后 ANN 索引毫秒级检索，外加持久化、增删改、元数据过滤。
**Q6 查询改写解决什么？** 模糊/口语/多意图 → 规范检索词，提高召回。
**Q7 为什么 Rerank？** 粗排快但可能"看着相似没答到点"，精排重排提升精度，两阶段兼顾快和准。
**Q8 为什么按文本去重不按 URL？** 不同 URL 会转载相同内容，同 URL 不同 chunk 也可能重复，按文本才能真正去重、不占满 top-k。
**Q9 相似度阈值？不设会怎样？** 不设则任何文本都算出分数、矮子里拔将军硬凑，导致强答幻觉；阈值太高误杀相关、太低放噪声，需权衡。当前 demo 靠 top-k+评审+未提及兜底，阈值是可加的前置闸。
**Q10 检索不到怎么办？** 检索空/评审判定答不了→带反馈重检索≤2 次→仍无则明确回复"知识库未提及"，**绝不让 LLM 脱离资料裸编（RAG 防幻觉底线，别和 research_agent 的"topic 兜底"混）**。
**Q11 长上下文都几十万 token 了为何还要 RAG？** ①全塞每次都贵、token 不可控；②超长上下文有 lost-in-the-middle、中间信息利用率下降；③延迟高；④知识更新要每次重塞、海量文档物理塞不下。RAG 按需取料、省 token、低延迟、知识分钟级更新、可溯源。
**Q12 RAG vs 微调？** RAG 给"事实知识"（外挂、可更新、可溯源）；微调改"行为/风格/格式/领域能力"（改参数、不适合记事实）。优先级：prompt→RAG→微调；可结合（微调定行为、RAG 供知识）。论文 LoRA 微调教能力、RAG 供知识，正好两类。
**Q13 RAG 效果怎么评估？** 离线看检索召回率/上下文精度、生成忠实度(faithfulness)/答案相关性，构建问答标注集跑指标；小 demo 用 bad case 分析迭代（分块、top-k、阈值、rerank）。
**Q14 和 research_agent 区别联系？** RAG 是单一知识问答能力；research_agent 是把含 RAG 在内的多路检索编排进带反馈闭环的 Agent。RAG 可作为 Agent 的知识/长期记忆模块（项目一 rag_search 就是）。
**Q15 "RAG 是 Agent 记忆模块"怎么理解？** 短期记忆=messages/State+checkpoint；长期知识记忆=向量库 RAG（用时检索进上下文，像"回忆"）；用户偏好等经历记忆存数据库按需召回。上下文是桌面、向量库是书架。

## 5. 避坑清单
- 别把"未提及兜底"说成把问题丢给 LLM 自由发挥（那是项目一开放调研的策略，RAG 必须防幻觉）。
- 溯源元数据是自己入库时存的，Milvus 只负责存储和连带返回。
- 一个 chunk 一个向量，不是每 token 一个；在线只给问题算向量。
- 递归分块(在哪切) 和 overlap(相邻重叠多少) 是同一切分器的两个参数，不是两种模式。
- 向量检索是语义匹配，区别于 BM25/关键词字面匹配。
- Rerank 不是再检索一次，是对已召回候选重新算相关性排序。
