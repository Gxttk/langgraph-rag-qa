# 工具调用 Tool Calling 与 MCP

## Tool Calling 完整流程

工具调用是让大模型能使用外部能力（搜索、计算、查库等）的机制，流程是固定的一个循环：

1. 绑定工具：用 bind_tools 把工具的名称、功能描述、参数 schema 告诉模型。
2. 模型决策：模型判断需要用工具时，在返回的 AIMessage 里带上 tool_calls 字段，里面只有“调哪个工具、传什么参数”的意图，模型本身并不执行工具。
3. 代码执行：外部代码（节点）按 tool_calls 调用真正的函数，拿到结果。
4. 结果回灌：把结果封装成 ToolMessage（带 tool_call_id 与调用配对），追加回消息历史。
5. 再次请求模型：模型读到工具结果后判断是继续调工具还是给出最终回答；若还有 tool_calls 就重复 2-4，直到没有 tool_calls 才输出最终答案。

关键点：模型只负责“决定调什么”，真正执行和把结果送回去的是外部代码。

## 固定工作流 vs 动态工具调用

- 固定工作流（workflow）：开发者用图把执行路径写死，确定、可控、便于调试、token 成本可预测，适合流程稳定的任务，例如本项目“检索→评审→生成”路径不变，因此直接在节点里调用检索，不必让模型临场选工具。
- 动态工具调用（agent）：模型在运行时根据问题自主决定调哪些工具、调几次，灵活、能应对开放场景，但路径不可预测、可能多轮烧 token。
二者不是对立，复杂系统里常把稳定主干做成工作流，把开放的子步骤交给工具调用。

## 并行与多工具

可以一次绑定多个工具，模型也可能在一条 AIMessage 里并行返回多个 tool_calls，由代码并发执行后一起回灌，减少往返轮次。

## MCP 是什么

MCP（Model Context Protocol，模型上下文协议）是一套统一的“工具/数据源连接协议”。它解决的是“工具怎么接进来”的问题：工具方按标准实现一个 MCP Server，客户端（Agent）用统一方式发现和调用它，新增一个数据源不用再为它单独写一套适配代码。

Tool Calling 解决的是“模型决定调哪个工具”，MCP 解决的是“这些工具以什么标准被接入和调用”，两者是上下层配合关系，并不冲突。
